### 目的から導かれる設計方針

安い相談枠を数多く撒くのではなく、**「診断 → 提案 → 受託」の動線が自然に成立する商品**を置く。
相談型を主軸にすると「教える人＝作らない人」と認知され、受託への導線がむしろ弱くなるため、
出口商品（見積型の開発）を最初から並べる。

## 4. 各商品の設計

### ① AI活用の現状診断書 — 5,000円

- **カテゴリ**: IT・プログラミング > AI活用・開発
- **お届け目安**: 5日 / **無料修正**: 1回

**「無料修正1回」の定義**: 診断書の記述の訂正・補足に限る。**前提条件が変わった場合の再診断は含まない**
（例: ヒアリング時に伝えられていなかった業務が後から出てきた場合は再診断となり、別料金）。
出品文に明記して認識のズレを防ぐ。①②とも同じ定義とする。

**工程**

1. ヒアリングシート（Googleフォーム）に回答 — 業務内容・繰り返し作業・使用中ツール・月の作業時間
2. 任意で30分オンライン（ovice）で補足ヒアリング
3. 3営業日で診断書（PDF）を納品
4. 納品後7日間、DMで質問対応

**納品物の構成**

| 章 | 中身 |
|---|---|
| 1 | 業務フローの棚卸し（現状を図で1枚に） |
| 2 | AI・自動化で置換できる工程の特定と削減見込み時間の試算 |
| 3 | やる順番を3分類 — 今すぐやる1つ / 3ヶ月後 / **やらない方がいいもの** |
| 4 | ツール選定と理由（Claude Code / n8n / GitHub Actions / スプレッドシート の使い分け） |
| 5 | 概算ランニングコスト（月額） |

**差別化の核: 「やらない方がいいもの」を書く**

市場のAI系出品はすべて「AIで解決します」と言う。対して ShiftCraft では、シフト生成を
**ナーススケジューリング問題（数理最適化・制約充足）と判断し、LLM をシフト生成に使わない**
と結論している。LLM の役割は自由文をルールに変換する入力インターフェースのみに限定した。

「AIを使わない方がいい領域を、根拠を示して指摘できる」ことが診断書の信頼性の源泉になる。

**提示できる裏付け**

- 受託2件の工数削減率 約90%（10人日 / 従来想定90〜100人日、5人日 / 同45〜50人日）
- n8n の運用コストを月$4〜5 → $0（Railway解約 → WSL2 + Docker Engine + Cloudflare Tunnel）
- 同じ「自動化」でも n8n ではなく GitHub Actions を選んだ判断の実例
  （うちなーマネーの変更検知。ローカルPC依存にする理由が無いため）
- Claude API の原価防衛設計（PreMeet: 1生成ごとに `cost_usd` を算出し上限 $0.15 と照合）

| 発見したバグ | 内容 |
|---|---|
| `ikunavi` | 産後パパ育休の計算で `Math.min(28, 終了−開始のミリ秒)` と括弧位置を誤り、支給額が常に0円。月額30万・28日取得で `0円` → `187,600円`。公開中のAPIから呼ばれていた |

さらに Cloudflare Workers 固有の実バグも自力で特定・修正している。

- `ikunavi` の sitemap.xml の `loc` が `https://ikunavi.example.workers.dev/` になっていた。
  原因は `wrangler.jsonc` の `vars` に残ったプレースホルダが Worker 実行時に `process.env` へ載り、
  `SITE_URL` のフォールバックが効かなかったこと。canonical・OGP・JSON-LD も同じ値を参照していた
- `app/robots.ts` ではなく Cloudflare 管理の robots.txt が配信されており `Sitemap:` 行が出ず、
  サイトマップは GSC への直接送信が必要だった
